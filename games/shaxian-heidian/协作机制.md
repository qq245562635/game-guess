# 沙县黑店：协作机制

三方怎么分工、东西放哪、按什么顺序推进。所有人开工前读一遍；规则有变，改这份文件。

**一句话原则：仓库是唯一的事实来源。三方之间只通过仓库里的文件和 PR 交接，聊天里定下的事必须落到文件里，否则不算数。**

---

## 一、角色与职责

| 角色 | 谁 | 负责 | 不做 |
| --- | --- | --- | --- |
| 制作人 | 你 | 定目标和优先级；提新需求、砍需求；最终验收"好不好玩、好不好看"；合并美术 PR | 不直接改代码和清单（告诉 Claude 改） |
| 程序 + 项目管理 | Claude | 写代码；维护需求清单、检查脚本、看板和本文件；验收美术交付、写退回意见 | 不改美术图的像素；不把没验收的图放进游戏；不自行加需求 |
| 美术总监 | Codex 出图 | 按需求清单出图、自查、走 PR 交付；按退回意见重画 | 不改代码、不改清单和状态；不直接推 main |

**拍板权**：要不要做、先做什么，制作人说了算。图合不合规格，以检查脚本和清单为准；规格本身有争议，由制作人决定后 Claude 改清单。

## 二、文件分工：每样东西只有一个地方

| 要查什么 | 看哪里 | 谁能改 |
| --- | --- | --- |
| 协作规则 | 本文件 `协作机制.md` | Claude（制作人同意后） |
| 要哪些图、规格、每张图的状态 | `美术需求与上传规范.md` 第三节 | Claude |
| 每次验收的结论和退回原因（历史） | `art/README.md` | Claude |
| 自动检查规则（尺寸、目录、透明等） | `tools/check_art.js` 里的 `SPEC` | Claude，**必须和上面的清单同一次提交里改** |
| 当前进度、谁在做什么、卡在哪 | `进度看板.md` | Claude |
| 美术图本身 | `art/<目录>/` | 美术，**只能通过 PR** |
| 退回的原图（只作对照） | `art/_rejected/` | Claude |
| 规格变更后作废的旧图（只作对照） | `art/_obsolete/` | Claude |
| 给美术的尺寸/位置参考图（程序画的占位图） | `art/_templates/` | Claude |
| 风格设定图 | `docs/art-reference/` | 美术（走 PR），制作人定稿 |
| AI 大图转原生像素图 | `tools/pixelize.js` | Claude 维护，美术使用 |
| 代码 | `src/` `tools/` | Claude |

**规则**：同一件事不在两个地方各写一份。看板只写"进行中/卡住/下一步"，具体每张图的状态以规范第三节为准。

## 三、美术图的状态

每张图在规范第三节的清单里有且只有一个状态：

```
待做 ──美术开 PR──▶ 已提交 ──验收通过──▶ 已入库
                       │
                       └──验收不过──▶ 退回 ──美术重画开 PR──▶ 已提交
```

| 状态 | 含义 | 谁改 |
| --- | --- | --- |
| 待做 | 还没交过 | — |
| 已提交 | 有 PR 在等验收（清单里写上 PR 编号） | Claude 收到 PR 时改 |
| 退回 | 验收不过，原因写在 `art/README.md` | Claude |
| 已入库 | PR 已合并，游戏里在用 | Claude |

**同一张图退回 2 次**：停下来，不要第三次直接重画。制作人和 Claude 一起看是提示词的问题还是需求本身的问题，改好了再画。

## 四、一轮美术交付的流程

| 步骤 | 谁 | 做什么 | 产出 |
| --- | --- | --- | --- |
| 1 | 制作人 | 定这一批画什么（如"P0 重做 + P1 角色"） | 在群里说一句 |
| 2 | Claude | 更新清单、提示词、看板；需要的话补检查规则 | 一次提交，说明以 `需求：` 开头 |
| 3 | 美术 | 按清单和第七节提示词出图，逐张自查（规范第五节） | — |
| 4 | 美术 | 开 PR：分支 `art/月日`，说明以 `美术：` 开头 | PR 链接发群里 |
| 5 | 自动 | PR 上自动跑 `check_art.js`，不通过会显示红叉 | 红叉就先自己修，不用等人 |
| 6 | Claude | 人工看图 + 放进游戏截图，逐张给结论 | PR 评论 + `art/README.md` 验收记录 + 清单状态 |
| 7 | 制作人 | 看截图，同意就合并 PR | 图进入游戏 |
| 8 | Claude | 把退回的图写清原因，更新看板 | 下一轮的输入 |

**一个 PR 的范围**：

- 一个 PR 只交一批，不混 P0 和 P1（分开开两个 PR）。
- 每个 PR 不超过 15 张，角色的 `_0` `_1` 必须一起交。
- 同一张图在 PR 里改了，直接往同一个分支再传，不要另开 PR。

## 五、批次与优先级

- **定调门槛**：定调的几张（现在是 `stove` `worker_0` `worker_b0`）通过之前，其他图只能画、不能合并。风格没定下来就批量入库，返工最贵。
- **风格基准**：2026-10-17 起以《烟火像素 V2》设定图为准（`docs/art-reference/`），斜 45° 等距视角，场景精灵按原生像素交图。定调是 `stove.png`（48×48 炉灶模块）、`worker_0.png` 和 `worker_b0.png`（24×32 斜前、斜后）。
- **P0 和 P1 可以同时画**，但验收按 P0 → P1 → P2 的顺序；P0 的 PR 优先看。
- **占位兜底**：没交或没通过的图，游戏里自动用程序画的占位图，所以美术和程序互不阻塞，可以分批交。
- 新加的需求默认排在当前批次之后，除非制作人明确说插队。

## 六、需求变更

1. 制作人提出（改规格、加图、砍图、换优先级）。
2. Claude 在**同一次提交**里改：规范第三节清单 + `check_art.js` 的 `SPEC` + 看板。提交说明以 `需求：` 开头，写清改了什么、为什么。
3. Claude 在群里告诉美术改了哪几张。
4. 如果改的是**正在画或已提交**的图，清单里那一行备注"规格已改，以新规格为准"。

**禁止私下约定**：美术和程序之间口头说"这张改成 128 宽吧"不算数，没写进清单的规格不验收。

---

## 七、Claude 每次开工和收工

Claude 在不同对话之间不会自动记得进度，所以：

- **开工**：先读 `进度看板.md`、本文件、规范第三节，再看仓库里最近的提交和打开的 PR。
- **收工**：把这次做了什么、卡在哪、下一步写回 `进度看板.md`，和代码一起提交。

---

## 八、提交和分支命名

| 类型 | 提交说明开头 | 分支 | 谁 |
| --- | --- | --- | --- |
| 美术交付 | `美术：` | `art/月日`（如 `art/1018`） | 美术 |
| 需求变更 | `需求：` | main | Claude |
| 验收记录 | `验收：` | main | Claude |
| 代码 | `沙县黑店：` | main 或功能分支 | Claude |

---

## 九、沟通

- 群里只发三类消息：**PR 链接**、**决定**（"P1 先做角色"）、**卡住了**（"这张画了 3 次都不对"）。
- 讨论出结论后，由 Claude 写进对应文件；以文件为准，不以聊天记录为准。
- 对某张图有意见，写在 PR 里那张图的评论下，不要只在群里说。
